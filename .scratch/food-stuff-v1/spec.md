# Food Stuff V1

Status: ready-for-agent
Published: November 15, 2026

## Problem Statement

Choosing routine dinners takes more effort than the household wants to spend each week. A meal idea still requires finding a usable recipe, choosing quantities, checking ingredients on hand, making a shopping list, comparing grocery options and entering products into a cart. Repeating that work discourages planning even when the meals themselves are simple.

The household needs a reusable personal tool that proposes a small complete plan, accepts easy corrections and carries the result through to grocery shopping. The user should review meaningful choices rather than manage an inventory system, inspect a dense form or repeatedly enter the same ingredients. Sourced recipes must remain identifiable and trustworthy; plausible model-generated cooking details are not an acceptable substitute.

## Solution

Build a local dinner planner followed by a separately launched desktop shopping skill. The planner proposes sourced recipes, lets the user replace one meal independently, presents recipe-listed extras as checkboxes, accepts an optional stock snapshot and derives a simple editable shopping list. A covered-first comparison of recipe requirements and purchase amounts leads to a saved approved shopping list.

The desktop skill reads that exact approval without ingredient retyping, uses the selected built-in browser session to compare a bounded set of available grocery stores, and prepares a reviewable cart. The user performs final cart review and checkout.

Use the existing ChatGPT subscription route for text, supported images and recipe discovery. Begin live recipe discovery with Good Food and RecipeTin Eats. Save source-backed cooking information for consistent reuse, with short bullet-point methods primarily for meal selection and original links for cooking.

Deliver the planner through durable shopping-list approval first, then connect desktop shopping, then validate one real week. Both planner and shopping remain required for V1. The preliminary live cart trial is deferred rather than made a planning prerequisite.

## Implementation Decisions

1. **Application shape.** Use one local TypeScript application: React Router Framework mode with Vite in SPA configuration for the React interface, Fastify for the local server, SQLite through better-sqlite3 for durable data, Tailwind CSS and a small set of shadcn/ui components for shared controls. Use generated route types and route-module/build conventions. Add only the components needed by the accepted flow and maintain their source as application code. Pin compatible releases during implementation rather than treating research or the earlier runtime inspection as a completed installation test.
2. **Local operation and frontend routing.** Fastify serves the built SPA assets and application endpoints from one local origin; use a development proxy rather than weakening origin checks. Configure React Router for SPA operation without runtime server rendering. Its shell is rendered at build time, so initial rendering must be safe without browser globals, credentials or live household data. Route client loaders/actions and fetchers call the shared application HTTP workflow and supply loading, mutation, error and revalidation behavior. Keep credentials, SQLite, auth callbacks and inference streaming on Fastify. Preserve deep-link navigation with an HTML fallback for UI routes only; API/auth failures must retain their real status and response rather than become the SPA shell. Bind to loopback initially. Responsive layout is required, while real phone-to-host connectivity remains a separate verification obligation. Keep credentials and private application data on the host rather than in client-delivered code or serialized route data.
3. **Configuration.** Centralize household size, batch recipe count and individual portions per recipe. Initial values are two people, two recipes and six individual portions each. Snapshot the active values with a week. Calculate complete household dinners per recipe and leftover individual portions without rounding partial coverage up. No settings page is required; later controls must be able to use the same configuration and logic. Keep runtime settings explicit and centralized as well: private storage and credential paths, export location, bind host/port, application origin and OAuth callback settings. Validate their coherence at startup while retaining exact callback, Host and Origin checks; do not scatter paths or addresses through application modules.
4. **Workflow module.** Provide a small public application workflow for proposing or loading a week, replacing a meal, recording extras and stock decisions, editing purchase amounts, deriving the current list, approving it and exporting the approval. It owns ordering, revisions, validation and durable state. Route modules call this workflow through HTTP; they must not duplicate calculations or become a second revision authority. Router revalidation refreshes views, and request cancellation or stale-response suppression does not replace transactional expected-revision checks or completed-only saving of AI results. The UI and main regression tests use the same application behavior.
5. **Internal modules.** Keep subscription access, recipe sourcing, week planning, shopping calculation, durable records and desktop handoff understandable as code modules within the application, not separate deployed systems. Use concrete dependencies and ordinary functions. Construct the application and its dependencies separately from the entry point that listens on a local port. Keep HTTP handlers thin and delegate to the shared workflow; startup owns binding and orderly shutdown, including closing database connections and other owned resources. Tests must be able to construct an isolated application without starting the normal listener. Introduce adapters at actual external variation points, including recipe sources and inference, without building a hypothetical provider framework or a test seam for every helper.
6. **Durable records.** Store planning configuration snapshots, explicit household preferences, weekly requests, sourced recipe versions, meal selections, stock observations and decisions, shopping-list revisions, approvals and cart results. Use local migrations. SQLite is the source of truth for plans, approvals and operation state needed to preserve revision and completion guarantees across restart; exports are immutable projections of approvals rather than a second editable store. Credentials and exports use explicit private paths. In-memory progress may be transient, but incomplete work must leave the last valid saved revision intact. A restart restores saved work without implying that an interrupted AI request continues or completes automatically.
7. **Identity and provenance.** Give weeks, recipe versions, selected meals, ingredients, list revisions and runs stable identities. A sourced recipe version retains its original URL or identifiable reference, title, author/publisher where available, source time/digest, base yield, source-backed ingredient/method information and short bullet preview. Retain enough field provenance to explain an interpretation without copying article text, photos or comments.
8. **Quantity representation.** Distinguish fixed quantities, ranges, equivalent measurements and unquantified requirements. Preserve unit, preparation and measurement basis. Use centralized deterministic arithmetic and delay display rounding. Equivalent cups and grams for one source ingredient are not additive. Dry/cooked or net/drained quantities cannot be combined without a justified conversion.
9. **Recipe sourcing.** Discover candidates live across Good Food and RecipeTin Eats initially. Reuse saved successful recipes without reducing the product to a fixed catalog. Retrieve the actual recipe material and consider its method and relevant notes as well as structured ingredient data. Normalize different source shapes for authors, yields and ordered instructions. A search result or generated citation alone is not a verified recipe.
10. **Faithful normalization.** AI may interpret and normalize retrieved source fields, select recipes, summarize a short method, interpret changes and propose stock observations. It may not invent ingredients, directions, yield, timings or adaptations. Validate normalized records before selection. Keep the original source readily accessible. Missing prep/cook splits stay unknown unless verified elsewhere in the source; cooking times are not multiplied by ingredient scaling.
11. **Incomplete candidates.** Try another suitable sourced recipe when retrieval is blocked or the candidate is incomplete. Explain the gap only when no suitable usable result can be found. Do not repair missing cooking information from model memory or overwrite a valid saved recipe with an incomplete result. Respect applicable source access conditions; technical retrieval is not a permission grant for public redistribution.
12. **Saved recipe behavior.** Save a verified base version and derive later serving changes from it. For ordinary source yield ranges, use the lower bound visibly; flag unusually wide or unclear yields instead of choosing unsupported precision. Short methods are bullet-point previews for choosing meals. Initially, cooking can use the original recipe; this does not require a standalone cooking mode.
13. **Independent meal changes.** Replacing a meal preserves the other meal selections. Validate model-proposed changes against the current draft revision before applying them. Temporary requests belong to the week and become persistent household preferences only when explicitly requested. Support saved successful recipes without silently changing their versions.
14. **Extras.** Use a distinct step containing only optional items, sides and serving suggestions from the selected recipes, grouped by meal with simple checkboxes. Permit selecting none. Defer app-generated extras, include/omit recommendations and explanatory provenance panels. If a source leaves an amount unspecified, preserve that fact separately from an editable purchase target such as an appropriate pack.
15. **Stock capture and corrections.** Photos are the main input, text description is secondary, and a single Continue action works with no stock supplied. When input is supplied, show observations for correction before finalizing deductions. Maintain a distinction between observed identity/presence, amount and user-confirmed purchasing decisions. Corrections override image guesses. Do not infer absence from invisibility or sufficiency from presence.
16. **Stock decisions.** Offer Enough, an exact or approximate amount, or Buy the full amount. Enough covers the requirement it was confirmed against, not an invented measured stock quantity; recheck it when that requirement increases. Preserve estimate labels. Buy the full amount resolves purchasing without asserting zero stock. Common seasonings may be assumed on hand but remain accessible and can be marked needed; do not extend that assumption automatically to all staples.
17. **Shopping derivation.** Aggregate compatible requirements across selected meals and extras, then apply effective stock deductions once. Propose mixed-unit estimates only with a visible basis and user confirmation. Keep incompatible preparations or unsupported conversions explicit. Purchase overrides change what to buy, not the original sourced recipe. Keep requirement, deduction, purchase amount and recipe membership traceable.
18. **Shopping interface.** Show item and purchase quantity in the main list. Keep amount editing stable in size. Covered items hide by default and can be revealed and restored. Make ingredient/source/quantity/stock details separately accessible and searchable; a side panel is an accepted starting pattern, not a mandated final visual design. Avoid persistent rows of controls, teaching examples and debugging panels in the user flow.
19. **Approval review.** Show ingredient, recipe-required amount and amount to buy, grouped into covered ingredients first and purchases second. Compact recipe tags may identify shared ingredients. Provide back navigation to the editable list. Do not replace this comparison with an otherwise empty approval summary or require a second dense editing workflow.
20. **Review flags.** Flags are advisory, explain their basis and require no per-flag acknowledgement. Missing stock information is subtle context, not a warning for each ingredient. Compare compatible recipe need against known usable stock plus purchase; preserve estimate labels and do not treat unknown stock as confirmed zero. Flag clear unexplained excess, accounting for ordinary pack sizes and intentional stock-ups. Do not impose a blanket twice-the-need rule. Preserve user edits and accepted stock-up choices. Invalid data types and negative quantities remain ordinary validation errors.
21. **Revision and approval rules.** Mutations use expected-revision checks and transactional saving. Changing selected recipes, portions, extras, effective stock decisions or purchase amounts invalidates approval. Navigation, filtering, showing covered items or opening a source does not. Approval captures the exact week/configuration/recipe/list version, time and content digest. Historical approvals remain available but cannot certify later edits.
22. **Subscription route.** Use host-side Sign in with ChatGPT with the granted plan-usage scopes and account-visible model discovery. Identity sign-in alone is insufficient for inference. Preserve the validated public-client behavior: stable host identity, initial dynamic registration, persistence of the issued client identity, fresh state/nonce/PKCE, identity-token verification and explicit plan-scope gating. Handle refresh scope changes and returning-user identity consistently. Keep exact callback and origin rules coherent. No separate API billing, provider fallback or OpenRouter integration is selected for V1.
23. **Inference completion and recovery.** Use the validated streamed Responses route, explicit needed context and non-stored request behavior. Only a completed response becomes successful saved output; partial, failed or interrupted streams do not replace valid data. Cancellation, retries and late responses cannot overwrite newer edits or create duplicate records. On consent, quota, expired-session or request failures, explain the problem and preserve saved work. Actual entitlement, model tools and limits remain account-dependent rather than guaranteed by the previous access proof.
24. **Handoff contract.** Export a schema-versioned JSON approval containing list identity/revision, approval time, digest, currency, stable ingredient identities, purchase targets, relevant constraints and quantity/source basis. Include uncertainty and unquantified purchase targets explicitly. Exclude tokens, browser state and the full delivery address. Write revision-specific exports atomically; a convenience pointer must not change the input of an active run silently.
25. **Pinned shopping runs.** The desktop skill validates and pins one approved version. Drafts, altered approvals and stale versions are not interchangeable inputs. If the plan changes during a run, stop applying the old plan and report it; accept the change only from a newly approved version. Save results with the same identity/revision/digest. A stale result may remain historical but cannot certify a newer list. Local result-file import is sufficient; a watcher or remote-trigger service is unnecessary.
26. **Built-in browser execution.** The shopping skill runs separately in the selected local built-in browser profile. The validated connection method opened the target website in a fresh chat's own browser pane before discovering and controlling it. Check actual runtime availability and existing delivery context; do not change address or silently switch to a different browser/profile. Report missing tools rather than extracting cookies or using private browser-protocol workarounds. The planner's inference route does not itself supply browser control.
27. **Basket comparison.** Start with approximately two actual address-available stores and prefer a complete basket at one store. Calculate suitable product/pack counts, availability, surplus and CAD costs. Record observation time. Missing items make a basket incomplete. Include visible fees, taxes and promotion conditions; unknown charges remain unknown rather than zero. Claim only cheapest among the checked comparable candidates and qualify any missing delivered-cost information.
28. **Buying defaults.** Keep perishable purchases near the planned need. Larger packs can be suitable for freezable meat, dry staples and long-lived sauces, after considering on-hand stock. Show material excess and extra cash required for stock-ups; low unit pricing alone does not justify unwanted perishable surplus. These preferences are defaults, not permission to ignore the approved list.
29. **Cart changes and result ledger.** Observe and record the cart baseline, intended task additions, product identities/options/pack sizes and observed outcome. Repeat runs target the required task quantity rather than appending it. Newly approved versions reduce or remove identifiable stale additions while preserving unrelated quantities. Ask when independent user changes make ownership unclear; do not clear the whole cart. Inspect uncertain outcomes before retrying because a timeout does not prove failure.
30. **Gaps and replacements.** Select equivalent brands and suitable packs within the approved constraints without interrupting for every ordinary product choice. Complete the work that can be done, then gather missing ingredients and meaningful replacements into one review. Changes affecting a sourced recipe or household constraints remain pending review. Record unresolved gaps honestly; do not report a fully completed cart based only on attempted clicks.
31. **Checkout and privacy.** Leave the cart ready for the user's final review and stop before checkout. Keep credentials, photos, shopping snapshots, cart results and precise delivery/account context in private local data, outside tracked source and ordinary logs. Credentials stay on the host. The prototype credential storage was access-controlled, not encrypted; verify the real storage protection and describe it truthfully. Bound source retrieval, redirects and photo input, and treat retrieved content as untrusted data.
32. **Build order.** First deliver the complete local planner through a durable approved shopping list, including subscription and source-backed recipes. Then connect and validate the desktop shopping skill, then try one real week. Routine framework/version and UI details should not reopen settled product choices. The previously proposed seven implementation tickets are still a breakdown proposal, not published or approved tickets under this spec.

## Testing Decisions

1. **Purpose and cost.** Give implementation agents a quick regression suite and a practical way to verify the UI they create. A good test checks an externally visible outcome or durable record, not a private method, component structure, CSS class, SQL statement or number of internal calls. Target a routine fast run of a few seconds, measure it when built and keep expensive checks separate; no current runtime benchmark is claimed.
2. **Integrated planner tests as the default.** Exercise the public application workflow used by the UI, preferably through its local HTTP interface or equivalent highest application entry. Use real calculation, revision, validation and persistence behavior together to catch interactions such as recalculation, stock deduction, approval invalidation and reload. One primary seam is a default, not a limit justified by having one user flow. Tests may begin from a known saved draft and exercise one action; they need not repeat the entire weekly journey. The public interface must serve real UI callers as well as tests.
3. **Real isolated local persistence.** Each integrated planner scenario gets a disposable database and known starting data. Construct an isolated application with explicit temporary paths and a disposable database. Exercise saving, closing and reopening the application, conflict behavior and preservation of the last valid state after interrupted work against the real persistence implementation. Verify invalid or incoherent runtime settings are rejected and retain focused checks for callback, Host and Origin handling. Isolate test databases, photos and handoffs from actual household records. Control clocks and external identifiers only where stable assertions need them; do not make every internal operation injectable. Focused pure calculation tests do not need database setup.
4. **Controlled external responses and focused module tests.** Supply representative source pages and inference outputs at actual external IO seams. Use direct tests of useful module interfaces where many meaningful cases, an independent contract or substantially clearer failure diagnosis justify them: quantity/scaling calculations, source extraction and normalization, subscription protocol and handoff validation. Source tests must exercise normalization of retrieved material, not only accept already-normalized recipe fixtures. Integrated planner tests may use validated recipe fixtures for scenarios unrelated to extraction, while representative controlled-source cases verify wiring through normalization into saved recipes. Do not fake the planner or SQLite to make expected totals pass, expose every private helper for tests, or mock every internal module. Fixtures contain synthetic data or minimal public source facts, never real tokens, personal photos, cart snapshots or full copied articles. Include missing fields, inconsistent or incomplete content, uncertain stock, provider failures and interrupted streams.
5. **Quantity and configuration behavior.** Use focused table-driven tests for dense arithmetic, scaling and conversion cases, with representative integrated planner tests proving their use with stock, revisions and persistence. Cover the default week, a non-default household/recipe/portion combination, fractional household coverage and leftover portions. Verify source-yield scaling, lower-bound ordinary ranges, equivalent measures counted once, method-only ingredients, timing preserved independently, compatible aggregation, unsupported conversions remaining explicit and no premature precision claims. Avoid duplicating every calculation case through HTTP or Playwright.
6. **Stock behavior.** Cover no supplied stock, corrections overriding observations, unknown presence without a deduction, Enough versus an amount versus Buy the full amount, approximate labels, requirement increases invalidating old coverage, seasoning assumptions and their override, and one deduction across shared ingredients. Verify that user purchase edits do not rewrite source recipes.
7. **Revision and recovery behavior.** Drive meal replacement, extras, stock corrections and purchase edits through the primary workflow. Verify unchanged meals remain unchanged, temporary requests remain temporary, stale expected revisions are rejected, material changes invalidate approval and read-only actions do not. Reload after saving and after a simulated request failure. Late/cancelled results must not overwrite newer drafts or create duplicates.
8. **Review examples.** Need 500 g with unreported stock and a 500 g purchase: no warning. Need 600 g with 400 g confirmed stock and a 200 g purchase: covered. Need 500 g with 200 g confirmed stock and a 100 g purchase: advisory 200 g shortfall. Need 300 g broccoli with an unexplained 3 kg purchase: attention. Need 300 g with a 500 g bag: ordinary rounding. Explicit stock-ups do not repeatedly trigger the same concern. The user can approve advisory flags without individual acknowledgements.
9. **Focused subscription protocol checks.** The external authentication/provider contract is a necessary separate seam, not an invitation to mock all app modules. Use controlled protocol responses to check fresh state/nonce/PKCE, registration identity, callback rejection, identity/scope verification, refresh behavior, visible model filtering, bounded image/text requests and completed-versus-incomplete streams. Test host/origin and request validation through public local HTTP behavior. Default tests use no real credentials or subscription requests.
10. **Focused handoff checks.** Verify that export content matches the approved version, writes are atomic, repeated exports do not invent a new approval, drafts/tampered inputs are rejected and stale results cannot certify newer plans. Synthetic cart-state cases cover task-owned versus unrelated quantities, safe repeats, revised reductions/removals and ambiguous independent changes. They validate the contract and expected decisions, not actual grocery website reliability.
11. **Agent UI verification.** Use supported Computer Use/browser tools for exploratory checks of the runnable local app after meaningful UI changes, alongside the repeatable Playwright suite. Agents should follow the accepted flow with safe fixtures, inspect the rendered result and record the scenarios actually verified. Check keyboard operation, editable dictation-compatible fields, independent alternatives, extras, empty-stock Continue, stock corrections, stable quantity editing, hidden-item recovery, searchable details, bullet previews and covered-first review. Do not claim success from code inspection alone or make a tooling failure look like an application failure.
12. **Critical browser regressions from the start.** Include a small checked-in Playwright Test suite as the first runnable planner flow is built. Initially cover the sourced-meal-to-approved-list workflow (including an independent meal replacement, extras, optional stock and purchase edits), saved state and approval surviving reload, and a material edit invalidating approval. Include direct navigation/reload of supported UI routes and a focused HTTP check that unknown API/auth requests retain errors instead of returning the SPA shell. Test observable route behavior, not generated route types or framework internals. Verify user-visible outcomes and relevant persisted results. Start with one Chromium configuration, automatic local-server startup, isolated browser contexts and disposable seeded databases, controlled AI/source responses, pinned browser dependencies, user-facing locators and web-first assertions. Keep it separately runnable from the fast workflow suite and run both for relevant changes. Retain failure traces/reports for diagnosis; avoid fixed sleeps, layout-internal assertions, live credentials and live grocery interactions. Agents may explore and propose tests or repairs, but assertion changes, weakened expectations and new skips require review; retries do not establish that a flaky test is healthy. A large browser matrix, screenshot-baseline system and agent-tooling installation are not prerequisites.
13. **Live checks are separate and opt-in.** Use a small live smoke/acceptance suite for real subscription access, source retrieval and desktop grocery behavior. Do not run it as part of ordinary regression tests. Contract fixtures check request/response handling; live checks detect external drift that fixtures cannot. Keep request counts bounded, report whether a failure is environment/access/provider/application-related and never introduce a separate billing route to make a check pass.
14. **No automatic real-cart regression runs.** The selected grocery integration is a supervised browser skill rather than a provider test API. Test its real behavior during implementation with an explicitly scoped session and approved shopping list. Verify product pack arithmetic, visible costs and unknown fees, a repeat without duplicates, a newly approved change and preservation of unrelated items. Respect active tool requirements, leave checkout to the user and keep account evidence out of Git. The preliminary planning trial remains deferred; do not reintroduce it as a prerequisite or silently run live cart changes.
15. **Prior art.** The preserved subscription prototype has 13 local protocol, protected-storage and HTTP checks. Their examples include authorization transaction freshness, explicit plan-scope gating, wrong-state rejection, returning-client consistency, visible model filtering, explicit conversation context, bounded image input, stream parsing and origin/callback behavior. Reuse their useful behavior and fixtures after review, not the throwaway UI wholesale. Source-fidelity and planner prototypes provide concrete acceptance examples and limits, not a completed regression harness. There are no production application tests on the main checkout yet.
16. **Developer workflow.** Expose documented commands for the fast workflow suite and the small Playwright regression suite; keep live checks separately invoked and opt-in. Run focused relevant checks during implementation, then the required regression checks before completion, including browser tests when the change affects their flows. Record actual results and limitations. Broaden or repeat checks when a change, failure or unresolved concern warrants it, not as a ritual. Validate one real week after the planner and desktop skill are connected.

## Out of Scope

- AI-generated recipes, invented recipe variations or completion of missing source details from model memory.
- Lunch planning, nutrition optimization, assigned weekdays, continuous stock maintenance, multi-household accounts and a settings UI.
- A standalone cooking mode; the bullet method is a meal-selection preview and the original recipe remains available for cooking.
- App-generated extras or include/omit recommendations; V1 extras are recipe-listed optional items and serving suggestions.
- Custom audio recording, transcription, live voice or spoken replies. OS dictation supplies editable text.
- OpenRouter, multiple AI providers, a separate API billing account or an automatic paid fallback.
- Runtime server-side HTML rendering, experimental React Router API-only mode, replacing Fastify with a full-stack React server, public hosting, remote-trigger automation, distributed infrastructure, a background result watcher and automatic network exposure of the local host.
- Arbitrary web-wide recipe coverage, a fixed starter collection as the final discovery system or public redistribution of recipe articles and images.
- A fixed supported grocery store list, universal cheapest-price claims, multi-store checkout optimization or direct delivery API integration.
- Automated checkout, payment or order placement.
- A mandatory preliminary live cart trial or replacement mock during planning. Functional cart validation still belongs to implementation acceptance.
- Comprehensive UI automation, a broad browser/device matrix, mandatory screenshot baselines or tests mirroring every internal implementation detail. The small critical-flow Playwright suite is in scope.
- Merging a prototype branch wholesale, modifying the preserved subscription stash, or treating prototype smoke tests as proof of production correctness.
